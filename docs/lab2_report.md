## 5. Чек-лист тестирования от QA
## Позитивные сценарии:

1. [ ] **Создание проекта**: POST /api/projects с телом {"title": "Новый проект"}. Ожидается: статус 200, проект добавлен в БД.

2. [ ] **Получение проектов**: GET /api/projects. Ожидается: статус 200, JSON-массив с проектами.

3. [ ] **Создание задачи**: POST /api/tasks с телом {"title": "Сделать ТЗ", "project\_id": 1}. Ожидается: статус 200, задача создана.

## Негативные сценарии:

1. [ ] **Создание задачи без названия**: POST /api/tasks с пустым title. Ожидается: ошибка 422 (Unprocessable Entity).

2. [ ] **Создание задачи для несуществующего проекта**: POST /api/tasks с project\_id: 9999. Ожидается: ошибка базы данных (Foreign Key constraint fails) или 404.

## Бизнес-логика (Автоматический статус):

1. [ ] **Блокировка проекта**: Создать задачу со статусом "Blocker" для проекта id=1. Ожидается: при следующем GET /api/projects статус проекта id=1 изменился на "Blocked".

## 8. Вывод
В ходе выполнения лабораторной работы были успешно освоены ключевые навыки декомпозиции комплексного функционального требования на независимые подзадачи по INVEST-критериям. В роли тимлида я спроектировал единый API-контракт в формате OpenAPI 3.0 и настроил автоматический CI-пайплайн для проверки качества кода через GitHub Actions. В процессе интеграции компонентов бэкенда и фронтенда возникли небольшие трудности с согласованием форматов дат, которые были оперативно разрешены благодаря строгой привязке к Swagger-спецификации. Полученный опыт командной реализации, настройки ветвлений и взаимного код-ревью позволил наладить эффективное взаимодействие в команде. Извлеченные уроки по обязательному покрытию тестами и раннему обсуждению контрактов будут напрямую применены в следующем спринте.
