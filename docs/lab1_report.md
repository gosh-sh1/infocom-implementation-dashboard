Цель работы:
Освоить практические навыки инициализации проекта и организации командной разработки программного обеспечения с использованием Git, GitHub, Kaiten и Docker.
Для достижения поставленной цели необходимо выполнить следующие задачи:

  1	Создать репозиторий GitHub и подготовить структуру проекта.
  
  2	Настроить ветвление по методологии GitFlow с использованием веток main, develop и feature/*.
  
  3	Разработать регламент командной работы в файле CONTRIBUTING.md.
  
  4	Создать проект в Kaiten, сформировать основную карточку «Инициализация проекта» и распределить задачи между участниками команды.
  
  5	Организовать разработку отдельных модулей проекта и их интеграцию посредством Pull Request.
  
  6	Провести Code Review, проверить изменения и выполнить слияние проверенных Pull Request в ветку develop.
  
  7	Подготовить Docker-окружение для запуска Backend, Frontend и PostgreSQL.
  
  8	Подготовить отчёт о проделанной работе с подтверждающими скриншотами.

Ход выполнения работы:
1. Создание репозитория GitHub
На первом этапе был создан репозиторий infocom-implementation-dashboard, предназначенный для совместной разработки панели управления внедрением информационных систем.
Для организации работы использовалась платформа GitHub. Участникам команды предоставляется доступ к репозиторию, необходимый для создания веток, отправки изменений и участия в проверке кода.
В репозитории предусмотрены следующие основные элементы:
•	README.md - описание проекта и инструкции по запуску;
•	CONTRIBUTING.md - правила работы с ветками, коммитами и Pull Request;
•	.gitignore - список файлов и каталогов, исключаемых из системы контроля версий;
•	LICENSE - лицензия проекта;
•	backend/ - серверная часть приложения;
•	frontend/ - пользовательский интерфейс;
•	docs/ - документация и отчёт;
•	docker-compose.yml - конфигурация совместного запуска сервисов;
•	.github/ - шаблоны Pull Request.
Начальные служебные файлы добавляются при инициализации репозитория. Структура приложения и остальные компоненты разрабатываются в отдельных ветках с последующим слиянием в develop.

2. Организация ветвления по GitFlow
Для контроля изменений была выбрана упрощённая схема GitFlow, предусматривающая использование стабильной ветки main, интеграционной ветки develop и отдельных веток для выполнения задач.
Назначение основных веток:
•	main - стабильная версия проекта, содержащая проверенные изменения.
•	develop - интеграционная ветка, в которую добавляются результаты работы участников после проверки Pull Request.
•	feature/* - временные ветки для разработки отдельных компонентов и выполнения конкретных задач.
Для работы Team Lead используется ветка:
feature/IC-01_teamlead_initial_setup
Она создаётся на основе develop. В ней выполняется подготовка структуры проекта, документации и регламента командной работы.
Для остальных участников предусмотрены отдельные ветки:
•	feature/IC-01_backend_initial_setup;
•	feature/IC-01_frontend_initial_setup;
•	feature/IC-01_devops_initial_setup.
После завершения работы участник отправляет изменения в GitHub и создаёт Pull Request с целевой веткой develop. Прямое внесение изменений в main и develop в рамках обычной разработки не используется.

3. Подготовка структуры проекта и регламента командной работы
В ветке feature/IC-01_teamlead_initial_setup подготавливается структура проекта и создаются необходимые служебные файлы.
Предусмотренная структура репозитория:
infocom-implementation-dashboard/
├── backend/
│   └── Dockerfile
├── frontend/
│   └── Dockerfile
├── docs/
│   └── lab1_report.md
├── docker-compose.yml
├── CONTRIBUTING.md
└── .gitignore
Содержимое каталогов backend/ и frontend/ дополняется соответствующими разработчиками. Конфигурация docker-compose.yml подготавливается для последующего объединения сервисов.
В файле CONTRIBUTING.md фиксируются основные правила командной разработки:
-	Использовать отдельную ветку для каждой задачи.
-	Применять согласованный формат названий веток.
-	Оформлять коммиты в соответствии с Conventional Commits.
-	Создавать Pull Request для внесения изменений в develop.
-	Указывать описание выполненной работы и ссылку на соответствующую задачу Kaiten.
-	Проверять изменения и устранять замечания Code Review до слияния.
Для оформления коммитов используется формат:
<тип>(<область>): <краткое описание>
Примеры:
•	feat(backend): add health endpoint;
•	feat(frontend): add project homepage;
•	chore(docker): configure compose services;
•	docs(readme): add project instructions.

4. Настройка доски Kaiten
Для организации и контроля выполнения задач используется Kaiten. На доске «Панель управления внедрением ИС» создаётся основная карточка «Инициализация проекта», к которой относятся четыре задачи, соответствующие ролям участников.
Если отдельный тип карточки «Эпик» недоступен, основная карточка создаётся как обычная карточка, а задачи связываются с ней доступным в рабочем пространстве способом.
Содержание задач:
Задача IC-1 - Инициализация репозитория и структуры проекта.
Ответственность Team Lead. Включает создание репозитория GitHub, подготовку структуры каталогов, создание CONTRIBUTING.md, настройку веток и проведение итогового Code Review.
Задача IC-2 - Разработка Backend.
Ответственность Backend Developer. Включает подготовку шаблона серверного приложения, создание Dockerfile и реализацию endpoint /health.
Задача IC-3 - Разработка Frontend.
Ответственность Frontend Developer. Включает подготовку пользовательского интерфейса, создание Dockerfile и отображение названия проекта и состава команды на главной странице.
Задача IC-4 - Настройка Docker и интеграция.
Ответственность QA/DevOps. Включает подготовку docker-compose.yml для PostgreSQL, Backend и Frontend, создание .gitignore и шаблона Pull Request, а также проверку совместного запуска компонентов.
Задачи назначаются соответствующим участникам. В ходе выполнения работы их статусы изменяются в соответствии с фактическим прогрессом.

6. Подготовка Docker-окружения:
Для запуска компонентов проекта предусмотрена контейнеризация с помощью Docker.
Файл docker-compose.yml предназначен для описания трёх основных сервисов:
•	PostgreSQL - система управления базами данных;
•	Backend - серверная часть приложения;
•	Frontend - пользовательский интерфейс.
Для каждого приложения предусматривается собственный Dockerfile, описывающий сборку и запуск соответствующего компонента.
После объединения изменений необходимо проверить корректность конфигурации и совместный запуск сервисов командой:
docker compose up --build
Также проверяется доступность пользовательского интерфейса и endpoint /health серверной части.
Результаты проверки фиксируются скриншотами терминала и работающего приложения.
